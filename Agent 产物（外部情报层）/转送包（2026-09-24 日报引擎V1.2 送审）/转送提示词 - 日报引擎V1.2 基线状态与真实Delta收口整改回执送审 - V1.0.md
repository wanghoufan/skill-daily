## 四类问题的收口方式

1. **「不重复」≠「只报今天变化」（§一~§六/§十三/§二十七）**
   日报状态拆成两层：`candidate_baseline`（首跑为全池 1106 条建签名基线，baseline_seen）
   与 `shown`（用户真见过）。daily_delta 模式每条 item 必须有今日理由
   （真事件 / action 迁移 / 项目新匹配 / 签名变化 / 反馈变化 / 冷却到期且曾被展示），
   未展示 backlog 一律 `suppressed.baseline_backlog`，永不轮播；
   Day1 脚注只报数量（实测：9 条静态候选未展开，观察 9；它们次日不出现）。
   每条 item 带 `report_reason_type`（六枚举，禁 static_backlog_rotation）+
   `material_today_evidence`，`why_today` 由 reason 生成；
   Day1 文案为「为什么出现：首次建立 Skill 基线…」，不再是「今天进入安装候选」。
2. **缺 External snapshot 全池假 NEW（§七~§十一）**
   Delta 优先级链：日报自有 candidate_baseline → 外部 last_snapshot（仅首日辅助，
   辅助时缺键不判 NEW）→ 都没有则零事件。仍复用 v2.11 classify_delta/snap_key。
   实测（解包场景 A）：首跑 delta_source=none_first_run_zero_new，NEW 条目 0，
   旧风险不再被假 NEW 激活（risk 只认相对上次展示新增的事件）。
3. **包内产物口径不一致（§二十~§二十二）**
   `reports/package-e2e-audit.txt` 由【最终 zip 解包字节 + v2.11 转送包】实际运行生成，
   包内 Day1 日报 / DAILY_REPORT_CONTEXT.json / daily_snapshot.json / repeat-audit /
   feedback-demo 全部取自同一隔离环境同一轮运行；t59 断言包内 Day1 keys == 审计 DAY1 keys
   （10/10 一致）。场景 A：DAY1 10 / DAY2 0 / DAY8 9（全部 cooldown_reminder，
   未展示 backlog 出现 = []）；场景 B（开发仓含外部快照）：Day1 同样 10 条同 keys，
   Day2 changed_total=0 → 0 条。
4. **绝对路径泄露（§二十三~§二十五）**
   input_provenance 只写 logical_path（external-intelligence/... 等）；
   真实路径仅 `SKILL_DAILY_DEBUG_PATHS=1` 时进 runtime_debug_path，默认不写。
   对最终 zip 解包树 grep `/Users/ /home/ C:\ /Volumes/` = 0 命中（t60/t61 断言）。

V1.1 全部保留：全动作冷却 / 同日幂等 / PRIMARY+alternatives（共享提醒状态）/ 族配额 /
真 SKIP / C.CANDIDATES_PATH / 中文 one_line / unchanged_repeated_items=0。
